EMPECEMOS POR LO ESENCIAL

¿Qué es la arquitectura monolítica?

Es un enfoque donde las partes principales de una aplicación se construyen y se ejecutan juntas como un sistema integrado.

01 / CONCEPTO

Una aplicación completa,
con responsabilidades distintas.

En un monolito, la interfaz, las reglas del negocio y el acceso a los datos forman parte de una misma aplicación. Sus módulos colaboran dentro del mismo proceso, por ejemplo llamando funciones internas, en lugar de necesitar una llamada de red entre servicios.

Al construir la aplicación, sus componentes suelen compilarse y probarse juntos. Después se publica como una unidad: una sola versión contiene las capacidades necesarias para ejecutar el producto.

✳

Un ejemplo cotidiano: una tienda en línea puede administrar usuarios, productos, pedidos y pagos desde una misma aplicación. Cada área tiene una tarea, aunque todas se entreguen juntas.

PIEZAS DE UN MISMO CONJUNTO

Características principales

El enfoque monolítico describe la integración y el despliegue, no impide crear límites claros dentro del código.

Código integrado

Las funcionalidades forman parte de la misma aplicación. Ejemplo: el catálogo y el carrito están en el mismo producto de software.

Módulos organizados

El código puede separarse por responsabilidad. Por ejemplo, usuarios y pagos tienen carpetas y reglas propias.

Despliegue conjunto

Una nueva versión suele incluir el sistema completo, aunque el cambio afecte solo al catálogo.

Comunicación interna

Los módulos pueden llamarse directamente dentro del mismo proceso, como una función de inventario usada al crear un pedido.

Desarrollo centralizado

Construcción, pruebas y depuración suelen ocurrir en el mismo proyecto y entorno de desarrollo.

Recursos compartidos

Los módulos pueden reutilizar bibliotecas, configuración y, si el diseño lo permite, estructuras de datos comunes.

Escalado de la aplicación

En la configuración habitual se agregan recursos o instancias al sistema entero, no solo a un módulo.

ELEGIR TAMBIÉN ES ENTENDER LOS COSTES

Un comienzo simple, con límites que observar

Las ventajas y desventajas dependen del diseño, del tamaño del sistema y de las prácticas del equipo.

+
CUANDO APORTAN VALOR

Ventajas

Fácil para empezar

Un proyecto pequeño puede avanzar sin coordinar muchos servicios y despliegues.

Estructura inicial sencilla

El equipo trabaja sobre un proyecto y un flujo de ejecución comunes.

Desarrollo y despliegue directos

En muchos casos hay menos piezas de infraestructura que preparar y mantener.

Pruebas y depuración locales

Es posible ejecutar buena parte de la aplicación en un solo entorno.

Comunicación interna rápida

Los módulos pueden colaborar sin llamadas de red entre servicios.

Menos operación distribuida

Frente a una solución distribuida equivalente, suele requerir menos coordinación operativa inicial.

−
COSTES A TENER EN CUENTA

Desventajas

Mantenimiento más difícil al crecer

Sin límites claros, los cambios en una zona pueden afectar muchas otras.

Despliegue de toda la aplicación

Una modificación pequeña puede requerir publicar una nueva versión del conjunto.

Escalado menos selectivo

Normalmente se agregan recursos para el sistema completo, incluso si una función concentra la carga.

Fallos con impacto amplio

Un error grave puede afectar al proceso o a toda la aplicación.

Acoplamiento entre equipos

Compartir código o datos sin límites claros puede dificultar el trabajo independiente.

Construcción y pruebas más largas

En sistemas grandes, validar una modificación puede requerir probar mucho más que el módulo cambiado.

Estas desventajas no son inevitables: influyen la calidad del diseño, el tamaño del sistema y las prácticas de desarrollo.

DOS ENFOQUES, DISTINTAS NECESIDADES

Monolito vs. microservicios

Ningún enfoque es siempre superior. Elige según el tamaño, las necesidades y la capacidad operativa del proyecto.

Aspecto Monolito Microservicios
OrganizaciónUna aplicación; puede tener módulos internos.Servicios separados por capacidades de negocio.
DespliegueEl conjunto suele publicarse como una unidad.Cada servicio puede publicarse por separado.
EscalabilidadHabitualmente se escala toda la aplicación.Es posible escalar servicios de forma selectiva.
ComunicaciónLlamadas internas dentro del proceso.Comunicación por red y contratos entre servicios.
Complejidad operativaMenor al inicio: menos procesos distribuidos que operar.Mayor: redes, despliegues y observabilidad distribuidos.
MantenimientoSencillo al inicio; puede dificultarse si crece sin límites claros.Cambios localizados, con coordinación entre servicios.
Independencia de equiposEl código compartido puede requerir coordinación.Los equipos pueden tener más autonomía si los límites están bien definidos.
Cuándo encajaProyectos pequeños o medianos, equipos reducidos o producto en evolución.Cuando se necesitan despliegue y escalado independientes y se puede asumir su complejidad.
DECISIÓN CON CONTEXTO

Empieza por las necesidades reales

Un monolito modular puede ser una base práctica para un proyecto pequeño o mediano. Si el producto y el equipo crecen y aparecen necesidades concretas de despliegue o escalado independiente, se puede evaluar separar capacidades. La arquitectura debe resolver un problema, no añadir piezas por moda.
